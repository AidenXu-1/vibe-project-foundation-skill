# Agent 协作规则

> 这是所有 AI Agent 共用的工作规则。`AGENTS.md` 和 `CLAUDE.md` 只做入口,不要重复写长规则。

## 读取策略

先读本次必要内容。当前上下文中已读且未变的内容可沿用；缺失、变化或冲突时补读。

| 场景 | 必读 | 按需读 |
|------|------|--------|
| 开发或修复任务 | `docs/spec.md` 中与本次任务相关的段落 | 首次进入、接班或进度影响判断时读 `docs/progress.md` |
| 技术选择 / 新依赖 | `docs/spec.md`、`docs/decisions/` 中的相关决策 | `docs/conventions.md`、已有实现与依赖 |
| 接续中断工作 | 已启用协作层时按本部门接班入口恢复；否则读 `docs/progress.md` | 相关代码和决策；需要恢复环境时读 `app/README.md` |
| 大改方向 | `docs/spec.md`、`docs/roadmap.md`、`docs/decisions/` | 项目首页的产品简介 |
| 写代码 | 本次相关 Spec 段落、`docs/conventions.md`、本次改动涉及的代码与调用流程 | 相关测试、已有相似实现 |

局部文字修正、只读问答等任务先查相关内容；涉及需求或范围判断时再补读相关 Spec。

长输出保留原文，先查退出状态、汇总与失败位置，再读相关段落；缺失、截断或矛盾时扩大范围，筛选为空不能判定通过。引用已读内容用已有路径，确需行号时只补相关段落。

开发以已确认需求和 `docs/spec.md` 为准。辅助文档有误时直接修正；需求已变时按“变更控制”更新 Spec，无法判断时再问。

## 实现取舍

在满足已确认功能、体验和可靠性的前提下,选择实现、验证和后续维护总成本较低的方案。

- 先理解任务和实际调用流程。修改共享函数前查找全部调用处并核对受影响路径，在共同根因处修复，避免各处重复打补丁；读取跟着问题走，不默认全仓审计。
- 依次检查：当前是否需要 → 项目已有实现 → 标准库 → 平台原生能力（如原生控件、CSS、数据库约束）→ 已有依赖 → 最小必要新增。找到满足要求的方案即止；几行清楚的代码能完成时，不为它新加依赖，也不另写选型报告。
- 优先直白表达；一个清楚的表达式或函数能完成，就不加无用包装。新增接口、工厂、配置项、文件或文档须有当前用途，不为猜测的未来需求预留；沿用现有布局，不为少几行牺牲可读性或职责边界。
- 自检本次改动是否重复同一业务规则、新增层次是否有实际用途。先考虑删除已确认多余的逻辑，再考虑叠加补丁；只合并同义逻辑，不连带清理无关代码。
- 简化须满足明确要求，保留外部输入校验、数据保护、权限检查、必要异常处理和可访问性。同样简洁时选边界处理更可靠的方案；涉及真实设备时保留必要校准，不按理想精度删参数。
- 验收标准以已确认需求和适用的项目约定为依据，必要时核对相关可信资料。能直接推导的自行整理，用关键场景的起始条件、操作和可观察结果说明；已有明确标准直接复用。缺少依据的产品取舍或数值阈值单独列为待确认建议，不自行定案，也不从现有实现倒推应有行为。
- 非平凡逻辑须有可重复运行的有效检查。优先沿用相关验证，按风险补最小检查，覆盖受影响的关键逻辑、失败路径和真实用户出口；不固定测试数量、不强制新框架，也不为无逻辑变化的修改凑测试。
- 检查实际结果，不能仅以内部调用成功证明功能正确。修复时优先确认检查能在原问题存在时发现错误，并在修复后通过；无法安全复现时说明验证边界。验收标准或检查有误时，按需求依据修正并说明理由，不以通过检查为由降低要求。
- 已确认范围内可逆的实现细节直接决定。简化有实际容量、性能或精度上限时，在相关代码附近说明限制与升级条件；影响产品使用的已接受限制按 `docs/spec.md` 记录。范围、体验或风险发生实质变化时再请用户决定，不自行缩减已确认功能。

## 开发节奏

1. **Foundation**:只搭地基,不选技术栈,不写业务代码。
2. **Spec v0**:先写清楚问题、用户、场景、边界和成功标准。
3. **Risk Check**:先找最大风险,可能是需求、UI、数据、权限、成本或技术可行性。
4. **Spec v1**:冻结 MVP 合同,写清功能范围、技术路线、验收标准和不做什么。
5. **Kickoff**:用户确认后再初始化 `app/`,补齐命令、环境变量示例和首次可运行验证。
6. **Build Loop**:一次只做一个功能切片,计划 → 实现 → 验证 → 按需更新进度 → 按项目约定提交。

上述阶段用于项目起步和方向变化。已确认范围内的小修复沿用现有 Spec、技术路线和布局,不重跑地基、选型或设计流程;计划和记录按实际复杂度简写。

## 阶段门槛

- **进入 Spec v1 前**:必须说清目标用户、核心场景、MVP 范围、不做什么、验收标准和主要风险。
- **进入 Kickoff 前**:必须完成风险检查,把结论写入 `docs/spec.md` 或 `docs/decisions/`,并确认是否需要 UI 原型、数据验证或技术小实验。
- **初始化 `app/` 前**:必须得到用户确认的技术路线,重要选择写入 `docs/decisions/`;代码布局按 `docs/conventions.md` 确定。
- **进入 Build Loop 前**:项目必须能以空骨架启动或通过最小验证。

## 改动前检查

- 写代码或改文件前先看当前变更状态,确认有没有用户或其他 Agent 留下的未提交改动。
- 不要覆盖、删除或回滚不属于本次任务的改动;如果这些改动影响当前任务,先向用户说明再继续。

## 改动分级

授权按本次行动的实际影响判断。用户已经明确授权的范围与动作持续有效,不因进入下一内部步骤重复询问;新增范围、风险或缺少用户独有信息时再确认。

- **A 级:高风险**。删除用户数据、改变权限/认证/支付/密钥行为、发送消息、调用付费 API、改部署或影响关键合同的大重构。说明方案与回退方式；已有授权未覆盖时再确认。
- **B 级:用户可感知**。功能、UI、文案、单模块业务逻辑。动手前简述意图,做完验证。
- **C 级:局部可逆**。文档、注释、typo、测试、小范围整理。可直接做,但仍要说明结果。

## 安全边界

- 未经用户确认,不提交 `.env`、token、密码、私有链接、手机号、邮箱、身份证等真实敏感信息;必须出现时优先用示例、脱敏或环境变量。
- 新增依赖先按“实现取舍”检查现成能力;确有必要时简述用途和风险,是否需确认按改动分级判断。
- 不理解的代码先查用途、调用和相关验证;仍有影响本次判断的未知信息时再问,不要直接删。
- 删除用户数据、付款、权限授权、发送消息、发布内容、生产配置和外部付费 API 须有覆盖该动作的明确授权;普通代码精简按改动分级处理。
- 实验脚本、调试输出、临时大文件放 `scratch/`(用完即弃,不提交);正式测试按 `docs/conventions.md` 定的布局归位。

## 完成标准

本轮交付按用户要求的范围判断；开发与自测可以先交付，后续独立审核、验收和正式收口仍按项目约定办理。默认简述结果、验证与实际限制；用户要求或判断需要时再展开，不逐段复述代码。交付须满足:

- 改动符合 `docs/spec.md`。
- 已验证,并说明怎么验证。
- 影响后续工作的信息变化时，按下节更新 `docs/progress.md`；启用协作层后由统筹汇总，部门只回报必要变化。局部文字修正等无实质进度变化的任务，在完成回复或 TASK 中说明即可。
- 一个完整功能切片完成后按项目提交约定处理;启用 Agent Team 时遵守其正式收口要求,暂不提交则说明原因。

## 当前工作说明

`docs/progress.md` 只保留继续工作所需的目标、状态、未解决问题与关键发现、下一步；区分已完成、已验证和未验证。

- 更新时替换过时状态，删去已解决且不再影响后续工作的过程记录；阶段结束也保留未解决问题和跨阶段约束，不按日期不断追加日志。
- 长期有效的需求、约定和重要决策归入现有对应文档，避免重复抄写；值得防止复发的问题优先落实为测试或必要代码注释。难以重现且重查成本高的发现，确有用途才另留简短说明。
- 不强制保留流水、原文证据链接或阶段总结。历史只在当前问题需要或用户要求时查阅，不默认加载归档。

清理文件只能减少以后读取的内容，不能抹去已进入会话的历史；沿用当前工具的上下文压缩机制，不要求每阶段新开会话。

## 变更控制

长期维护产品的大改不要直接进代码。先在回复或 `docs/spec.md` 里说明:

- 改什么
- 为什么改
- 影响哪些页面、数据、接口或文件
- 如何验证
- 如何回退

所需授权已覆盖时直接更新 Spec 和代码；新增范围、风险或尚待用户决定的取舍，先取得对应确认。

## UI / 设计可视化确认

- 设计预览仅在用户明确要求或任务列为交付物时制作。已确认方向下的普通 UI 实现、局部修复和文案调整直接推进,不因涉及界面而额外制作设计稿。
- 需要预览时交付可直接查看的结果和入口,尽量与实现同源;用户要求可编辑产物时保留可编辑性。可用现有设计工具、可打开图片或本地页面,工具受限时简述限制并选能满足交付要求的替代方式,不自动转入安装或工具排障流程。
- 用户要求“先看效果再做”时,等该方向确认后再实现。尚未确定的关键视觉或交互取舍仍请用户判断,实质偏离已确认方向时重新确认;同一方向无需重复审批。
- 最终按真实运行页面、App 或构建/打包结果验收,覆盖本次改动影响的用户可见状态和失败路径。单独设计预览不能代替真实用户出口验证;有差距或未覆盖项应说明。
