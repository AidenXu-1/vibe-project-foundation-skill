# Agent 协作规则

## 读取策略

改一句文案或回答具体问题，直接查对应内容。需要找回上次进展时，普通项目看[当前进度](progress.md)，启用 Agent Team 的部门看本部门接班记录。

开发和修复按任务查[需求](spec.md)、相关代码及适用的[项目约定](conventions.md)。选型时查[相关决策](decisions/)，启动项目看[应用说明](../app/README.md)。已读且未变的内容可以沿用。

## 范围与授权

需求以用户最近确认的内容为准，变更写回规格。涉及已有功能或数据的大改，动手前写清原因、影响、验法和回退方式。

已授权范围内，可逆的技术选择由助手决定。遇到会改变产品范围、体验、费用或资料保存方式的未定取舍，说明实际差别，请用户决定。

删除用户数据、改动权限或认证、付款或使用付费服务、对外发送或发布、修改生产配置、提交真实凭据或私人资料，都需要覆盖该动作的明确授权。配置和样本默认使用示例值。

## 实现取舍

- 动手前查看未提交的改动，保留他人的工作。修改共享代码先核对调用方。几处问题确有共同原因，就修在共同处。
- 选择能满足当前需求、便于验证和维护的简单做法。先看已有实现、平台自带能力和已有依赖，确需新增依赖时说明用途。
- 简化代码时保留原有校验、异常处理、资料保护及项目需要的无障碍或设备校准。容量或精度上限写在相关代码旁，影响使用的限制记在需求中。

新项目开工或方向大改时参考[路线图](roadmap.md)。日常修复沿用现有方案，改动按项目约定提交。

## 验证与交付

从已确认的需求确定怎么验。用用户实际会走的入口观察结果，按风险覆盖失败路径。对关键逻辑保留能重跑的检查，优先复用已有测试。修复问题时，尽量用同一项检查复现旧问题，再验证修复。若检查本身有误，按需求修正并说明依据。

读长日志先看退出状态、出错位置和汇总。结果缺失、截断或矛盾时回看原文。交付时说清做成了什么、实际验过什么。未验项只提影响使用或下一步决定的。项目另设独立审核或用户验收时，分别记录结论。

## UI / 设计可视化确认

用户要求预览时，交付能直接查看的入口。要求可编辑时保留源稿。约定先看效果再做，就等方向确认后实现。普通界面修改直接在实际页面或应用里验证。

## 当前工作说明

接班信息有变化时更新 [progress.md](progress.md)，写清当前目标、关键验证怎么重做及其结果、未决问题和下一步。启用 Agent Team 时，部门报变化，由统筹更新总进度。
